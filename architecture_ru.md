# ProductiveSocial — Обзор архитектуры

## Что это делает

Пользователи отслеживают свою работу — задачи, привычки, рутины и фокус-сессии — и система использует ИИ для анализа их продуктивности и начисления кредитов за нее. Бэкенд разделен на четыре сервиса: selfmanager управляет данными пользователя, timer отслеживает фокус-сессии, analytics выполняет ИИ-анализ, а billing отвечает за кредиты и вывод inference LLM. Перед этими сервисами расположены два дашборда Streamlit — один для пользователей, другой для администраторов.

---

## Сервисы

### `psocial_selfmanager` (Kotlin/Ktor, порт 1226)

selfmanager — ядро продукта. Он владеет всей моделью данных пользователя: проектами, задачами, привычками, рутинками и общей таблицей `users`, к которой подключаются другие сервисы.

Пользователи входят по email — без пароля. При первом вызове `POST /api/v1/auth/identify` создается их аккаунт и выдаётся JWT. При последующих вызовах находится существующий аккаунт, и возвращается новый JWT. JWT содержит claims с ID пользователя (целое число) и email, действует 24 часа. Токены обновления (refresh tokens) хранятся 30 дней и могут быть ротацией или отзывом по устройствам или глобально.

Каждому новому пользователю автоматически создается проект "Default". Проекты содержат задачи, привычки и рутины, удаление проекта — удаляет всё внутри. Задачи поддерживают сабзадачи (с учетом времени), запланированное время, теги (автоматически создаваемые при ссылке), и лог завершения. Привычки бывают двух типов — `Start` (формирование поведения) и `Quit` (его разрушение) — и отслеживают завершения с детализацией по сабзадам, связывая каждое завершение с конкретным запланированным временем. Рутины — упорядоченные последовательности шагов, каждый с длительностью и флагом автостарт, с логами завершения шагов.

Эндпоинт офлайн-синхронизации (`POST /api/v1/sync`) группирует все create, update и delete для всех сущностей в одном запросе. Клиенты задают свои UUID перед синхронизацией для идемпотентности при повторе. В батче могут ссылаться новые задачи на новые проекты в одном запросе. Ответ содержит отображение серверных ID, изменения с последней синхронизации, ошибки по отдельным элементам и список удаленных сущностей для очистки клиента.

selfmanager также предоставляет внутренние эндпоинты (X-Internal-Key) для других сервисов: analytics вызывает их для получения данных по задачам, привычкам и рутинам для формирования prompt для LLM; timer использует `POST /internal/time-log` для записи минут работы по задачам и привычкам после завершения сессии.

### `psocial_timer` (Kotlin/Ktor, порт 1227)

Таймер — трекер фокус-сессий по технике Помодоро. Сессии могут быть связаны с задачей, привычкой или рутиной из selfmanager или работать независимо. Он полностью автономен — пользователи могут отслеживать фокус-сессии и получать инсайты без участия selfmanager.

У каждого пользователя есть настройки, включающие длительность работы и перерывов, циклы до длинного перерыва и флаги предпочтений (автостарт, фокус-режим, звук, уведомления). При создании сессии текущие настройки снимаются в снимок — так история остается точной при изменениях. После накопления достаточной истории (минимум 5 завершенных интервалов работы, 3 коротких перерыва, 3 длинных перерыва) ответ включает рекомендации по длительности на основе среднего времени интервалов.

Жизненный цикл начинается с создания, автоматически стартует первый рабочий интервал. Потом пользователь переходит через интервалы: Работа → Короткий перерыв или Длинный перерыв (зависит от количества циклов относительно `cyclesUntilLongBreak`). После каждого завершенного рабочего интервала сервис возвращает **предложение перерыва** — Продленный отдых (если за день было 90+ минут фокуса без длинного перерыва), Длинный перерыв (если цикл достигнут) или стандартный Короткий перерыв. Каждая пауза также возвращает сигнал о риске заброса — сервис проверяет, достигнут ли порог пауз (на основе истории забросов или по умолчанию 3), или если сессия проста более чем в три раза дольше запланированного без завершений. При ручном завершении таймер вызывает `POST /internal/time-log` для начисления минут работы в selfmanager — "fire-and-forget", чтобы сбой selfmanager не мешал завершению.

Два эндпоинта инсайтов: `GET /insights/focus-patterns` группирует завершённые рабочие интервалы по часам и дням недели, показывая, когда пользователь наиболее продуктивен; `GET /insights/entity-stats` разбирает данные по завершённым сессиям, средним минутам работы и циклам по типу сущности (задача, привычка, рутина, отдельная сессия).

Офлайн-синхронизация (`POST /api/v1/pomodoro/sync`) работает как у selfmanager: батчи сессий и интервалов с постоянными UUID, сервер исключает дубли при повторе, ответ содержит отображение ID, изменения с последней синхронизации, ошибки и новую метку времени.

Таймер подключается к таблице `users` selfmanager напрямую через JDBC (HikariCP), а не через HTTP API — так создание пользователя работает даже при недоступности selfmanager, и один email всегда связан с одним `user_id` в обеих системах.

### `psocial_analytics` (Kotlin/Ktor, порт 1228)

Аналитика — слой ИИ и **единственный публичный вход для биллинга**. Она принимает JWT из selfmanager (общий секрет), чтобы не было отдельной авторизации. Все операции с кредитами — баланс, транзакции, депозиты — проходят через аналитик и не вызываются напрямую клиентами.

При запуске анализа (`POST /api/v1/analytics`) сервис собирает данные по задачам, привычкам и рутинам из selfmanager и статистику по pomodoro из timer (через внутренний ключ). Ошибки selfmanager и timer игнорируются — если один из них недоступен, данные пропускаются. Потом формируется структурированный запрос для биллинга, который выполняет проверку кредита, инференс LLM и списание. Ошибка биллинга возвращается пользователю. При успехе отчет сохраняется и возвращается.

Поддерживаются шесть типов анализа: `PRODUCTIVITY_SUMMARY`, `TASK_PRIORITIZATION`, `HABIT_INSIGHTS`, `ROUTINE_OPTIMIZATION`, `WEEKLY_TIMER_SUMMARY`, `CUSTOM`. Админский доступ контролируется через переменную окружения `ADMIN_EMAILS` — без базы данных. Админские эндпоинты дают системную статистику, управление отчетами и возможность предварительно создавать тестовые отчёты без затрат кредитов.

### `psocial_billing` (Python/FastAPI, порт 1229)

Биллинг — внутренний сервис учета кредитов и inference. Он не имеет клиента и таблицы пользователей. Все эндпоинты требуют `X-Internal-Key`. Пользователи идентифицируются только по `user_id` (целое число в виде строки).

Баланс не хранится в отдельной колонке — каждая транзакция фиксирует `balance_after`. Чтобы узнать текущий баланс, ищется последняя транзакция и читается `balance_after`. При первом обращении к новому пользователю создается автоматический депозит `DEFAULT_CREDITS_ON_REGISTER`. 

Прогнозы проходят через строгий жизненный цикл: проверка активной модели и достаточности кредитов, создание статуса `PENDING`, inference, и затем — `SUCCESS` (списание кредитов и хранение результата) или `FAILED`. Поддерживаются три провайдера: Ollama (локально), Anthropic Claude и OpenAI GPT. Также поддерживаются sklearn `.pkl` модели, загружаемые через joblib и вызываемые с `predict_proba`, если есть.

Регистрация модели хранится в таблице `ml_models`, где указывается название, тип, провайдер, ID модели, системный промпт, цена за предсказание и активность. На старте автоматически создается модель Ollama по умолчанию (UUID `fb96de86-3c73-489d-8f02-aaf8343d6101`, 5 кредитов).

### `psocial_dashboard` — Админка (Streamlit, порт 1230)

Доступна только для пользователей, чей email есть в `ADMIN_EMAILS`. Вход по email-only через selfmanager, статус админа проверяется сразу же вызовом эндпоинта analytics — если 403, доступ запрещен.

После входа админ может просматривать системные показатели биллинга, управлять пользователями, регистрировать и деактивировать модели ML/LLM, просматривать все предсказания и отчёты, а также управлять системными отчетами.

Все вызовы биллинга из админки используют `X-Internal-Key` — доверенный бэкенд.

---

### `psocial_user_dashboard` — Пользовательская панель (Streamlit, порт 1231)

Доступна любому зарегистрированному пользователю. Вход по email-only, нужен только JWT из selfmanager. Нет отдельного входа в биллинг.

Панель включает четыре раздела: **Продуктивность** — список задач, привычек, рутин из selfmanager; **Фокус** — две вкладки: Сессии с настройками и историей, метрики; Инсайты — рекомендации по длительности, графики паттернов фокуса, показатели завершений, генератор отчётов; Анализ — запуск анализа, выбор модели, история отчетов; Кредиты — баланс и история транзакций, через аналитик. Пополнение кредитов — только админ.

## Как соединяются сервисы

Все сервисы общаются по HTTP, через два канала:

### Клиент → Сервис (JWT bearer)
Пользователи и дашборды аутентифицируются, передавая JWT в заголовке `Authorization: Bearer`. selfmanager, timer и analytics принимают один и тот же JWT — секрет и издатель совпадают. Billing в этом канале не участвует.

### Сервис → Сервис (Internal Key)
Бэкенд-запросы используют заголовок `X-Internal-Key` с общим секретом. Переменная `INTERNAL_API_KEY` должна быть одинаковой для всех сервисов.

```
psocial_timer
  └── X-Internal-Key ──▶ psocial_selfmanager   POST /internal/time-log
                                                { entityType, entityId, minutesSpent, subtaskId? }
                                                fire-and-forget после завершения сессии

psocial_analytics
  ├── X-Internal-Key ──▶ psocial_selfmanager   GET /internal/users/{id}/tasks|habits|routines
  ├── X-Internal-Key ──▶ psocial_timer         GET /internal/users/{id}/stats
  └── X-Internal-Key ──▶ psocial_billing       POST /api/v1/internal/predict
                                                GET  /api/v1/internal/users/{id}/balance
                                                GET  /api/v1/internal/users/{id}/transactions
                                                POST /api/v1/internal/users/{id}/deposit
```

### Прямое подключение к базе данных (UserRegistry)
selfmanager и timer используют прямое подключение JDBC (HikariCP) к таблице `users` в базе данных selfmanager. Это не HTTP-запрос — прямое соединение. Используется только при `POST /auth/identify` для поиска или создания пользователя. В результате один и тот же email всегда дает одинаковый `user_id`, независимо от того, какой сервис вошел первым, и создание происходит даже при недоступности API другого сервиса.

```
psocial_selfmanager ──JDBC──▶ psocial_selfmanager_db  (таблица users)
psocial_timer       ──JDBC──▶ psocial_selfmanager_db  (таблица users — чтение/запись)
```

## Аутентификация

### Создание аккаунта и вход

Паролей нет. Везде используется **find-or-create по email**: отправьте email на `POST /api/v1/auth/identify` — и получите JWT, даже если аккаунт не был до этого.

```
Клиент → POST /api/v1/auth/identify  { "email": "user@example.com" }
       ← { accessToken, refreshToken, userId, expiresIn }
```

При первом вызове создается строка пользователя. При последующих — возвращается существующая. JWT содержит claims `user_id` и `email`.

### Обмен JWT между сервисами

selfmanager, timer и analytics используют один и тот же `JWT_SECRET` и `JWT_ISSUER`. Токен, выданный selfmanager, принимается timer и analytics без обмена — один вход даёт доступ ко всем трём.

**Billing не использует JWT.** Он полностью внутренний — все эндпоинты требуют `X-Internal-Key`. Клиенты к billing напрямую не обращаются.

### Обновление токена

selfmanager и timer поддерживают refresh tokens. `POST /api/v1/auth/refresh` обновляет токен и возвращает новую пару токенов. Эндпоинты выхода (`/auth/logout`, `/auth/logout-all`) отзывают один или все refresh tokens.

### Админский доступ

**Billing** — все операции админов защищены `X-Internal-Key`. В billing нет концепции административных аккаунтов.

**Analytics** — статус администратора определяется переменной окружения `ADMIN_EMAILS` (через запятую). Нет базы данных — изменение env сразу меняет список админов.

## Поток данных — AI-анализ (end-to-end)

```
Пользователь / Дашборд
  └─ POST /api/v1/analytics  { type, modelId }  (JWT)
       └─ psocial_analytics
            ├─ GET /internal/users/{id}/tasks      → selfmanager
            ├─ GET /internal/users/{id}/habits     → selfmanager
            ├─ GET /internal/users/{id}/routines   → selfmanager
            ├─ GET /internal/users/{id}/stats      → timer (статистика Pomodoro)
            └─ POST /internal/predict              → billing
                 ├─ авто-депозит приветственных кредитов при первом вызове
                 ├─ проверка баланса
                 ├─ создание структурированного промпта из данных пользователя
                 ├─ вызов Ollama / Claude / OpenAI
                 ├─ списание кредитов, лог транзакции
                 └─ возврат { текст инсайта, списанные кредиты }
  └─ аналитика сохраняет отчет и возвращает AnalysisResult пользователю
```
